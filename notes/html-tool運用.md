# 自作HTMLツールの置き場所（tiiny.host からの移行）

対象: 「当日張り込みカルテ」のような、**CSV → Python → HTML1ファイル** で作るツール。

## まず整理: ホスティングは「配布」しかしていない

生成されたHTMLは**完全に自己完結**（外部通信ゼロ・データ埋め込み済み）。
つまりファイルさえ iPhone にあれば動く。
tiiny.host が解決していたのは「**どうやって iPhone にファイルを届けるか**」だけ。
→ 月額を払う価値があるかは、この一点だけで判断してよい。

## 重要な前提: GitHub は HTML を「表示」してくれない

`raw.githubusercontent.com` は HTML を **text/plain（ただの文字）** として返す。
Private / Public を問わず、ブラウザで開いてもソースが見えるだけで動かない。
**HTMLを動く形で配信する機能は GitHub Pages だけ**で、それは常に全世界公開。
→ 業務データ入りのこのツールは Pages に置けない（`git-github.md` 参照）。

## 推奨: Private リポジトリ + Actions + ダウンロードして開く

1. Private リポジトリに **Python スクリプトと CSV** を置く
2. GitHub Actions で生成（`workflow_dispatch` = ボタン手動実行でよい）
3. 生成された HTML を**リポジトリにコミットさせる**
4. iPhone の Safari で GitHub を開き、そのファイルの
   **「Download raw file」**（ダウンロードアイコン）をタップ
5. Safari の**ダウンロード一覧（↓）からタップして開く**と JavaScript ごと動く

- 費用ゼロ / データは Private のまま外に出ない
- 過去バージョンが全部コミット履歴に残る（tiiny.host にはない利点）
- 注意: ファイルアプリのプレビューだと動かないことがある。Safari のダウンロード一覧か
  **Documents（Readdle社・無料）**アプリから開く

## 代替: Pyto でその場生成

Python が iPhone 内（Pyto）で完結するなら、**転送すら不要**。
生成 → ファイルアプリに保存 → 開く、で終わり。ネットも要らない。
CSV を手で書き集めている運用なら、こちらのほうが手数が少ないこともある。

## Actions のアーティファクトは使わない

Actions の「artifact」機能でも受け取れるが、**zip で降ってくる**ので
iPhone で解凍する手間が増える（ファイルアプリで長押し→展開）。
リポジトリに直接コミットさせるほうが早い。

# 重要: HTMLツールには「2種類」ある

置き場所の正解は**タイプによって真逆になる**。まずどちらか見極める。

| | **A. データ埋め込み型** | **B. データ書き込み型** |
|---|---|---|
| 例 | 当日張り込みカルテ | 先生の最優先メモ |
| 作り方 | Python が数字ごとHTMLに焼く | 空のアプリ。使う人が入力する |
| データの居場所 | **ファイルの中** | **ブラウザの中（localStorage）** |
| ファイル単体を人に渡すと | **業務データごと渡る** | 空のアプリが渡るだけ |
| ローカルで開く（file://） | ✓ 動く | **✗ 壊れる** |
| 正解の置き場所 | iPhone内 / Private リポジトリ | **GitHub Pages** |

## なぜ B はローカルファイルだと壊れるのか

**Safari は `file://` で開いたページに localStorage を使わせない**（セキュリティ上、
ローカルファイルは「どこの誰のページか」を特定できない＝オリジンが無いため）。

エラーで JavaScript が止まるので、画面は出るのに**ボタンが全部効かない**という
分かりにくい壊れ方をする。マイク（音声入力）も同じ理由で https:// が必要。

→ **B タイプは「ちゃんとした URL」がないと成立しない。**

## B タイプを GitHub Pages に置いてよい理由

**HTMLファイルの中にデータが入っていない**から。
入力された内容は各自の iPhone の中だけに保存され、GitHub には一切送られない。
公開されるのは「空のアプリ」だけ。他人がURLを開いても、その人の空の画面が出るだけ。

## B タイプの2つの落とし穴

### 1. データは URL に紐づく（引っ越すと消える）
localStorage は「そのURL専用の保存箱」。**別のURLに移ると中身は引き継がれない。**
tiiny.host から移す前に「📋 まとめをコピー」で中身を退避しておくこと。

### 2. 7日使わないと Safari がデータを消す
Safari には「**7日間アクセスがないサイトの保存データを自動削除する**」仕組みがある
（トラッキング対策。ITP と呼ばれる）。週1回しか使わないメモだと消えかねない。

→ **対策: Safari の共有ボタンから「ホーム画面に追加」する。**
ホーム画面のアプリは Safari 本体とは別扱いになり、**この7日ルールの対象外**になる。
B タイプでは追加は「見た目のため」ではなく**データを守るために必須**。

## B タイプの手順（iPhone / Safari）

1. https://github.com/new でリポジトリ作成。**Public** を選ぶ（無料 Pages の条件）
2. `Add file` → `Create new file` → ファイル名を **`index.html`** にする
3. HTMLの中身を**コピペ**（手打ちはスマート引用符で壊れる）→ `Commit changes`
4. `Settings` → `Pages` → Source を `Deploy from a branch`、Branch を `main / (root)` → `Save`
5. 1〜2分待つと `https://<ユーザー名>.github.io/<リポジトリ名>/` で開ける
6. Safari で開き、**共有 → ホーム画面に追加**

出典:
- https://webkit.org/tracking-prevention/
- https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage

# B タイプと「個人情報」— よくある誤解

## 事実: B タイプのHTMLファイルに個人情報は入っていない

「先生の最優先メモ」で言えば、**個人情報は入力された内容**であって、
それは **iPhone の Safari の中（localStorage）にしか無い**。

- HTMLファイル自体は**空のフォーム**。何度ダウンロードしても中身は空
- **tiiny.host のサーバーにも上がっていない。** tiiny は空のアプリを配っているだけ
- 入力内容がネットに出る処理は、このアプリのコードのどこにも無い（送信先ゼロ）

→ **GitHub Pages に置いても個人情報は公開されない。** 公開されるのは空のフォーム。

ただし「それでも公開URLは避けたい」は判断として正当（URLを知られたら
他人も同じ入力画面を使える、アプリの存在自体を知られる、等）。その場合は下記。

## 公開せずに使う3つの方法

| | A. 鍵付きURL | B. アプリを改造 | C. iPhone内サーバー |
|---|---|---|---|
| 中身 | Cloudflare Pages + Access | 保存方式を作り変える | WorldWideWeb 等のアプリ |
| 費用 | **年1,500円ほど**（独自ドメイン代） | 無料 | 無料（アプリ内課金あり） |
| アプリの改造 | **不要** | 必要 | **不要** |
| 設定の手間 | **大きい（一度きり）** | なし | ほぼなし |
| 使い勝手 | いまと全く同じ | 保存/読込が手動に | 毎回サーバー起動が必要 |
| ネット | 必要 | **不要** | 不要 |
| 7日で消える問題 | ホーム画面追加で回避 | **無関係（消えない）** | 起動のたび別扱いの恐れ |

### A. Cloudflare Pages + Cloudflare Access
静的サイトを無料で置ける Cloudflare Pages に、認証機能 Access を被せる。
**指定したメールアドレスの本人しか開けないURL**になる。
HTTPS なので localStorage も音声入力もそのまま動く＝**アプリは1行も直さなくていい**のが利点。

⚠️ **訂正: これは「完全無料」ではない。**
Cloudflare が最初にくれる `〇〇.pages.dev` というURLは
**Cloudflare 自身のドメインなので、Access で確実に保護できない**
（公式にも「所有していないドメインは保護できない」とある。
無理に設定すると「認証画面は出るのに素通りできる」中途半端な状態になりやすい）。

→ **確実に鍵をかけるには独自ドメインが要る。** Cloudflare Registrar なら原価販売で
年1,500円ほど（`.com` の場合）。tiiny.host の月額よりは安いが、無料ではない。

入口は製品紹介ページ（cloudflare.com/products/pages/）ではなく
**ダッシュボード（dash.cloudflare.com）→ Workers & Pages**。
GitHub の **Private リポジトリのまま連携できる**ので、置き場所は非公開にできる。

手順の全体像:
1. dash.cloudflare.com でアカウント作成
2. Workers & Pages → Create → Pages → GitHub の Private リポジトリを連携
3. Registrar で独自ドメインを取得（年1,500円ほど）
4. Pages の Custom domains にそのドメインを割り当て
5. Zero Trust → Access → Applications → Self-hosted でそのドメインを登録し、
   自分のメールアドレスだけ許可するポリシーを作る

### B. アプリを改造して完全オフライン化
**`file://` ではブラウザの自動保存が一切使えない**（localStorage も IndexedDB も
Cookie も全部ダメ。オリジンが無いため）。なので**保存方式そのものを変える**必要がある:

- 入力中はメモリ上に持つ
- 「保存」ボタン → JSONファイルとして書き出し、「ファイル」アプリに置く
- 開いたら「読み込み」ボタンでそのファイルを選ぶ

得るもの: 完全オフライン / 7日削除の心配なし / iCloud でバックアップ・世代管理できる
失うもの: 自動保存。**閉じる前に保存を忘れると消える**
注意: 音声入力ボタンは file:// では動かない（マイクは HTTPS 必須）。
iPhone キーボードのマイク入力で代替する。

### C. iPhone内でローカルサーバー
**WorldWideWeb – Mobile**（Iconfactory・無料）等でフォルダを配信し、
`http://localhost:8080/` で開く。localhost は「ちゃんとしたURL」扱いなので
**localStorage も音声入力も動く＝改造不要**。
難点: 使うたびにサーバーアプリを起動する必要がある。人に渡すツールには向かない。

## まとめ（どれを選ぶか）

- **オーナー自身が使う** → **B（改造）**。0円・アカウント不要・完全オフライン
- **改造せず今のまま使いたい** → **C**。ただし毎回サーバーアプリの起動が要る
- **他人に配る / どこからでも開きたい** → A。年1,500円と初回設定を許容できるなら

出典:
- https://www.cloudflare.com/plans/free/
- https://developers.cloudflare.com/pages/platform/known-issues/
- https://iconfactory.com/worldwideweb/

# 作ったもの: sensei-memo-offline.html

`files/sensei-memo-offline.html`（2026-08-26 作成）

「先生の最優先メモ」を **B案（オフライン対応）** に改造したもの。
**1ファイルで、ホスティングしてもオフラインでも動く**ように作ってある。

## 仕組み

起動時に「localStorage が使えるか」を試して、モードを自動で切り替える。

| 開き方 | 自動保存 | 画面の表示 |
|---|---|---|
| https:// でホスティング | **効く**（前と同じ） | 緑「自動保存：有効」 |
| file:// でダウンロード | 効かない | 灰/黄「無効」＋未保存警告 |

**元の版はこの判定が無く、file:// では `localStorage` が例外を投げて
JavaScript ごと停止していた**（＝ボタンが全部効かない）。そこを try で包んだのが肝。

## 書き出しの3段構え

iPhone のダウンロード機能は iOS のバージョンによって挙動が違うため、
確実な方法から順に試し、**最後は必ず手で運べる道を残す**:

1. 共有シート（`navigator.share`）→「ファイルに保存」が選べる。一番確実
2. ダウンロード（`<a download>`）→ iOS 18.2 以降は動かないことがある
3. テキスト表示 → 長押しでコピー。これは絶対に失敗しない

## 検証済み（Playwright / 各20項目）

http:// と file:// の両方で通過。file:// は **Safari が localStorage を拒否する挙動を
再現して**テストした（Chromium は素で許してしまうため、そのままでは検証にならない）。

- 追加 / 最優先 / 削除 / 全消し
- 書き出し → 全消し → 貼り付けて復元（最優先フラグ・最初の行動も復元）
- 壊れた入力を弾いてもデータが飛ばない
- 読み込んだデータに HTML が仕込まれていても実行されない
- **localStorage が使えなくてもアプリが落ちない**

## 使い方（オフライン運用）

1. ファイルを iPhone の「ファイル」アプリに保存
2. Safari のダウンロード一覧からタップして開く（またはDocumentsアプリ）
3. 使い終わったら **「💾 ファイルに書き出す」→「ファイルに保存」**
4. 次に開いたら **「📂 ファイルから読み込む」** で前回の続きから

音声入力ボタンは file:// では動かない（マイクは https:// 必須）。
**iPhone キーボードのマイクを使えば同じことができる。**

# iPhone でローカルHTMLを開く（決定版）

⚠️ **「ファイル」アプリから開くのは不可。**
iOS のプレビュー機能（Quick Look）は **JavaScript を必ず取り除く**仕様。
画面は表示されるのに**ボタンが一切効かない**状態になる。
さらに iOS 18 以降は、ファイルアプリから他アプリで直接開くこともできなくなった。

→ 使える道は次の2つだけ。

## 方法1: Safari のダウンロード一覧（推奨）

### ⓪ 先に設定を変える（これをしないと1日で消える）

**設定 → Safari → ダウンロード → 「ダウンロードリストからの削除」→「手動」**

初期値は「1日後」。翌日には一覧から消え、**↓ボタンごと画面から消える**。
「手動」にすれば自分で消すまで残り、毎日ここから開ける。

### ① Safari でダウンロードする

**Claude やメールから「ファイルに保存」したものは対象外。**
Safari 自身がダウンロードしたものしか一覧に載らない。

GitHub に置いてあるなら、Safari でそのファイルのページを開き
**ダウンロードアイコン（↓）**をタップ →「ダウンロード」を選ぶ。

⚠️ **実際にやると `〇〇.html.txt` という名前で落ちてくる**（2026-08-29 確認）。
GitHub が HTML を「ただの文字（text/plain）」として返すため、Safari が
「テキストファイルだ」と判断して `.txt` を付け足す。
**このままでは開いてもソースコードが表示されるだけ。**

→ 「ファイル」アプリ → ダウンロード → ファイルを**長押し → 名前を変更**して
`.txt` を消す。それから開く。

### ② ↓ ボタンの場所

**一度もダウンロードしていないと、このボタンは存在しない。**
ダウンロードすると**アドレスバーの横**（アドレスバーが下なら右端）に現れる。
最初は青い進捗の輪が回る。

### ③ 一覧の**ファイル名**をタップ

虫めがね（ファイルアプリで表示）ではなく、**名前のほう**をタップする。
Safari 内で開き、JavaScript が動く。

## 方法2: HTMLを実行できるアプリで開く

**Documents（Readdle社・無料）** など、内蔵ブラウザを持つアプリで開く。
ファイルアプリのプレビューと違い JavaScript が動く。
毎日使うならこちらのほうが手順が短い。

## 正直な評価: オフライン運用は手数が多い

ここまでで必要な手順を数えると:
設定変更 → Safari でダウンロード → `.txt` を消す → 専用アプリで開く →
使ったら書き出す → 次回は読み込む。

**iOS はローカルHTMLをアプリとして使うことを想定していない。**
データが入っていないアプリ（Bタイプ）なら、素直にURLに置いたほうが圧倒的に楽。
オフラインにこだわる価値があるのは、**ファイル自体に業務データが入っている
Aタイプ**（当日張り込みカルテなど）のほう。

## 補足: ホーム画面に追加はできない（2026-08-29 確認）

**iOS の「ホーム画面に追加」は `http://` `https://` のページ専用。**
ローカルファイル（`file://`）と `data:` URL では、共有メニューにこの項目が出ない。

理由: ホーム画面のアイコンは「URLを開くショートカット」でしかない。
ローカルファイルには**安定したURLが無い**（ダウンロードのたびにパスが変わる）ので、
指し示す先が作れない。

→ **アイコン一発で開きたいなら、URLに置くしかない。** これは設定や工夫の問題ではなく、
iOS の設計そのもの。

### ダウンロード一覧での2つのタップ先の違い

| タップする場所 | 開き方 | JavaScript |
|---|---|---|
| **ファイル名** | Safari 内で開く | **動く** |
| 🔍（虫めがね） | ファイルアプリで表示 | **消される** |

### さらに注意

iOS 18.5 以降、ローカルHTMLを Safari で直接開けなくなったという報告がある。
**開けるかどうかは iOS のバージョン次第。** Apple は年々この道を狭めている。
